# Real-repository harness (Milestone 1)

The whole existing eval suite is synthetic: every scenario is generated by the
same project that grades it, so nothing is proven outside its own fixtures. This
harness is the first thing that runs the product against a repository it did not
write.

**Milestone 1 is deliberately one repository, one injected defect, end to end,
with the honest result reported.** It is not a corpus. Proving the pipeline on
one real case is the deliverable; scaling to many repositories is later work that
would otherwise produce many unreliable numbers.

## The scenario

| | |
| --- | --- |
| Repository | https://github.com/openai/openai-quickstart-node |
| Commit | `6e6e03496440913a82ccba6f17c2f41caa948c58` |
| Licence | MIT (permissive; nothing is written back upstream) |
| Product | Fettler (impact analysis, deterministic path, LLM off) |
| Injected change | Provider removes `POST /v1/chat/completions`, superseded by the Responses API `POST /v1/responses` |

The change is realistic: it mirrors OpenAI steering developers off Chat
Completions onto the Responses API, and "an endpoint removed" is a canonical
provider move. It is expressed the way Fettler consumes a change — an OpenAPI
v1 -> v2 diff (`specs/openai-chat-completions-v1.json` -> `...-v2.json`) — not a
synthetic marker or magic token.

The repository is **not mutated.** The impacted call sites already exist in the
real source: every file that calls `openai.chat.completions.create`. Grading the
product on call sites the harness itself wrote would reproduce exactly the
synthetic self-grading this harness exists to escape.

## Ground truth and its isolation

The sealed answer key
(`answer-key/GROUND_TRUTH.fettler-openai-quickstart-chat-completions-removed.json`)
records the provider delta and the impacted call sites (files, symbols, lines),
hand-derived from the source with grep at the pinned commit — never from any
product output.

Isolation is enforced three ways, because a leaked answer key would make every
number meaningless (this project has already shipped one benchmark whose headline
was a label leak):

1. The clone lives OUTSIDE this git repo (`CLONE_ROOT`, default
   `../mp-realrepo-clones`), so a staged product cannot read the key off disk.
2. `harness.ts` calls the shared `assertCorpusRunIsolation`
   (`evals/runners/isolation.ts`) before the product runs, and
   `assertAnswerKeyUnreachable` on both the clone and the staged copy.
3. The repo is staged through `withStagedRepo` (`evals/runners/stage.ts`), which
   copies out only source and strips any `GROUND_TRUTH*` / `EXPECTED*` file — so
   the key name itself is defence in depth.

## Running it

```bash
# Clone the pinned commit (if absent), run through Fettler, grade, write report:
tsx evals/real-repo/run.ts

# Fail instead of cloning (clone must already exist):
tsx evals/real-repo/run.ts --no-clone
```

Output:
- `reports/<scenario>.md` — the evidence scorecard (committed).
- `reports/<scenario>.json` — the raw run result (gitignored; nondeterministic).

## Honesty rules this harness holds itself to

- **The headline is the real result, whatever it is.** True positives, false
  positives, and false negatives are all reported.
- **The injection was chosen before the run and is not tuned to the product.** A
  miss is a legitimate finding, not a bug to paper over.
- **"Found nothing" and "did not run" are distinct outcomes.** If analysis
  throws, refuses, or indexes nothing, the report says `DID NOT RUN`; it is never
  scored as a clean miss. This is the collapse this repository is most prone to.

## What is NOT wired

This harness is intentionally not added to `evals/scenarios/index.ts`,
`evals/readiness-gates.json`, or any GA gate. It must produce a trustworthy
result before anyone gates on it. `harness.test.ts` runs offline in CI (no clone,
no network); the live evidence run is manual.

## ReGauge

See the PR description for the assessment of whether ReGauge fits the same
harness. Short version: the substrate (clone + stage + isolation) is reusable,
but ReGauge is a recipe-application engine, not a spec-diff impact analyzer, so it
needs materially different scaffolding (a matching shipped recipe, workspace
execution, residual detection). That is Milestone 2, not something to half-build
here.
