# Internal API refactor consumer fixtures

Synthetic before/after consumer sources for the internal/custom API-refactor
family worked example, the `internal-api-acme-user-getuser-to-fetchuser`
provider recipe (see `docs/TRANSFORMER_API_REFACTOR_RECIPES.md`). No real
customer code. The internal team renamed the exported binding `getUser` to
`fetchUser` in the internal package `@acme/user-service`, and consumers must
update their imports and call sites.

This family is config/spec-driven, not a general refactorer. The recipe is built
from a spec `{ module: "@acme/user-service", from: "getUser", to: "fetchUser" }`
that is folded into the content-addressed recipe digest.

- `before/` — consumers on the recipe's supported surface. `src/profile.ts`
  imports `getUser` from `@acme/user-service` and calls it; `src/settings.ts`
  imports `getUser` alongside another named binding and calls it. Analysis
  classifies both as `applicable`.
- `after/` — the exact deterministic output of applying the recipe to `before/`.
  The import specifier and every bare `getUser(...)` call site become
  `fetchUser`; unrelated imports and the second named specifier are preserved
  byte-for-byte. Regenerated by the transform and asserted byte-for-byte in
  `packages/transformer/src/recipe-internal-api.test.ts`, so it never drifts.
- `out-of-scope/` — the classic false-positive trap. Both files call `getUser`
  and both import from the target module `@acme/user-service`, but the `getUser`
  binding comes from a DIFFERENT module (`@acme/admin-service`). Renaming it
  would corrupt an unrelated symbol, so analysis classifies this as `unsupported`
  (reason `recipe_internal_api_binding_unresolved`) and the recipe abstains.

Files are pinned to LF (`.gitattributes`) so the content-addressed digests are
stable across platforms.
